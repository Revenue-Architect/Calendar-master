## The one thing that actually matters and is still open

**Nobody has measured the navigation stutter on a phone.**

PR #11 rebuilt nav travel to stop animating `clip-path` per frame, and PR #12
fixed the corner regression that shipped with it. Neither closes the original
user report, because the defect is paint-bound and **headless Chromium cannot see
it** — it has no display pipeline and charges almost nothing for paint. Measured
here: a clean 60fps, median 16.7ms, worst 16.8ms, zero frames over 33ms, zero
Long-Animation-Frame entries. The same recorder caught the sheet morph at worst
50ms in the same session, so the instrument works.

`docs/plans/2026-08-23-001-fix-navigation-shell-clip-path-repaint-plan.md` §3 has
the gate. In short: remote-debug the phone, Rendering → **Paint flashing**, open
and close the nav. If the whole app surface flashes through the travel, it is not
fixed. A Performance capture showing Paint bars spanning the 520ms says the same.

Until someone does that, the honest status is *implementation complete, defect
unconfirmed*.

### Closed since the first draft of this handoff

- **Ribbon zero tab stops.** The first version of PR #13's roving stop left a
  browsed-out ribbon with no keyboard entry at all. `ribbonKeyboardAnchorIndex`
  now hands the stop to the browse position when the selection is unrendered,
  and back to the selection when it returns. Covered in
  `ribbon-readiness.spec.js`, negative-controlled, 50/50 on repeat. The companion
  keyboard-entry test was rewritten after review found it pressed `Tab` zero times
  (see *What I got wrong*); it now starts on `Previous day`, presses `Tab` once,
  with no loop and no fallback, and both keyboard tests re-gated at 100/100.
  `keyboardAnchorIndex` is also seeded synchronously in `useState` so the first
  painted frame owns the stop by construction — **that seeding is not test-covered**:
  `Planner` never unmounts in the re-entry flow, so no test in this suite can fail
  for it, and none is claimed to.
- **`toBeCloseTo(sample.progress, 0.08)`.** Not open debt — I read a mid-branch
  diff. `origin/main` already asserts
  `Math.abs(corner.scaleX - sample.progress) < 0.08` at
  `navigation-shell.spec.js:138`. PR #11's own corrective commit fixed it.
- **"Ten smart views, six chips."** Wrong as stated, and so is "all ten always
  render". `ActionsPanel.jsx:132` drops any view whose count is 0 unless it is
  selected or `today`, so the number rendered is **data-dependent**: one chip on
  an empty notebook, ten when every view is populated. With all ten rendered the
  row needs 1055px against a 650px column even at 1600px, so the overflow the
  edge fade exists for is not viewport-marginal. `README` and the surface agree;
  the earlier claim was one fixture mistaken for a rule.

## Environment — this remote box specifically

Everything in the 19 Aug handoff still applies. These are additions.

- **Playwright cannot find its own browser.** This image ships Chromium 1194;
  Playwright 1.62 wants 1234 and cannot download. Every run needs
  `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/opt/pw-browsers/chromium-1194/chrome-linux/chrome`.
  Without it you get ~58 identical "Executable doesn't exist" failures that look
  like a catastrophic regression and are not.
- **Use a distinct `PLAYWRIGHT_PORT` per run.** Ports were burned freely this
  session (4321, 4460, 4500, 4560…). A stale preview on a reused port serves the
  wrong bundle silently.
- **A scratchpad script cannot resolve `@playwright/test`.** Write probes into the
  repo root, run them, delete them. This is in the 19 Aug handoff and I hit it
  anyway.
- **`selectors.setTestIdAttribute("data-test")`** outside the Playwright config,
  or `getByTestId` matches nothing and reports it as a missing element.
- **Load contamination is real and it lied to me twice.** An `editor-rows` failure
  and a batch of `view-pills`/`typography` failures both evaporated on a quiet
  re-run. Check the wall clock of the run before believing any new failure — it is
  the cheapest lie-detector this suite has.
- Git worktrees under `.worktrees/` are gitignored and work well for bisecting;
  symlink `node_modules` in rather than re-installing.

## Method notes — what earned its keep, and what I got wrong

**What worked:**

- **Reading pixels beats reading screenshots.** I twice misjudged a rendered
  screenshot by eye — once calling a correct recessed card "wrong" because the
  shell (`rgb(23,24,27)`) and the surface (`rgb(10,10,12)`) are visually identical
  at a glance. Sampling the composited pixels through a canvas in a second page
  settled both questions in seconds and would have saved the wrong call.
- **Proving a cause by removing it.** Hiding only the four corner masks made
  PR #11's corner pixel-match `main`. That converted a hypothesis into a fact and
  named the fix at the same time.
- **Bisecting into a worktree.** Establishing that `motion.spec.js:503/727` fail
  at the exact commits that introduced them — that they had *never* passed —
  changed what those failures meant entirely.
- **Negative controls, every time.** All six new assertions in PR #13 were watched
  failing against the unfixed tree before being trusted (6 failed / 14 passed).

**What I got wrong, so the next session doesn't repeat it:**

- Grabbed an event card 14px from its top, landed in the desktop resize overlay,
  and reported "body drag resizes instead of moving". It was my grab point.
- Diffed task arrays index-wise and missed that dragging a recurring occurrence
  **appends** a detached task, concluding "action drag is broken" when it works.
- Predicted the eight transform walls would seam at fractional DPR, tested it at
  1/1.25/1.5/2, and found **no seam**. Worth recording as a negative: the
  geometry overlaps or abuts exactly, and the QA doc's reasoning that DPR checks
  matter less for this design is backwards even though its conclusion holds.
- **Broke focus-into-drawer with my own `inert` fix** and only caught it because I
  went looking for downstream impact. Making the drawer genuinely inert meant the
  focus call — issued in the same tick as `setPhase` — landed on an inert element
  and was dropped silently. One `requestAnimationFrame` was still too early; it
  needs two, which is what `useRibbonViewport` already waits for. **Nothing in the
  suite covered that behaviour.** It does now.
- **Wrote a keyboard test that pressed no keys, then cited it as proof.** The
  first version of "the browsed-out entry point takes focus by Tab" looked for the
  control before the strip via `day-ribbon.previousElementSibling`. That is `null`
  — `day-ribbon` is the *first child* of `ribbon-viewport`, and `Previous day` is a
  sibling of the viewport. The fallback focused the anchor directly, and the loop
  broke on its first iteration because `document.activeElement` already carried a
  `data-day`. Instrumented count of `Tab` presses it made: **0**. It passed 50/50
  and I put "`Tab` reaches the anchor" in the PR description on the strength of it.
  Caught in review, not by me. The repeat gate measured only how reliably the test
  avoided testing anything — **a green repeat count is not evidence that a test can
  fail.** Pair every new assertion with a negative control that reaches *the
  specific line* being claimed, not merely somewhere earlier in the test.

The lesson under all five: a green suite and a plausible screenshot are both
weaker evidence than a measurement of the thing itself.
